Les 4 modes de connexion SE ↔ SP — avec implications SSH/IP

Rappel : SP est une fonction (pilotage Node-RED), pas un appareil. Deux instances possibles : SP RPI (référence) et SP Smart (clone sur le Xiaomi, administré comme SE — Termux + SSHD). Vue complète des 4 scénarios : mqtt_reseau_V1.html.

#Contexte SESP actifAccès SP RPIImplication SSH/IP
1Box Wi-Fi maisonSP RPIAdresse locale directeSSHD RPi pertinent — même LAN, IP locale stable attendue
2Wi-Fi chez un tiersSP RPIDuckDNS (Internet)SSHD RPi via NAT box — IP locale SE inconnue/hors de contrôle
3Hotspot Xiaomi (4G active)SP RPIDuckDNS via passerelle 4G XiaomiSSHD RPi via NAT box — SE sur un subnet privé Xiaomi (hotspot), distinct du LAN du RPi
4Hotspot Xiaomi (sans 4G)SP Smart (Xiaomi)— (RPI non joint)SSHD Xiaomi pertinent (Termux+SSHD, confirmé) — SE et SP Smart sur le même LAN local
ℹ Les modes 3 et 4 se ressemblent (SE rejoint le même hotspot Xiaomi) mais diffèrent radicalement : en mode 3 le Xiaomi n'est qu'une passerelle vers Internet (SP reste le RPI) ; en mode 4 le Xiaomi devient SP lui-même, en pur local. Les questions SSH/IP à traiter sont donc différentes selon le mode : RPi (modes 1-3) vs Xiaomi (mode 4).
⚠ IP Webcam (visuel) à travers les 4 modes — problème réel identifié
Le mécanisme actuel de StreamURL ne fonctionne probablement que dans 2 modes sur 4.

rz_camera_manager.sh construit l'URL caméra comme http://{ip_locale_SE}:8080/video — quel que soit le scénario (WifiInternetBox, Wifi4KSP, WifiSPSsI produisent toutes la même forme d'URL). Cette URL n'est joignable que si SP est sur le même réseau local que SE au moment où il essaie de la consulter.
#SP et SE partagent le même LAN ?StreamURL joignable par SP ?
1 — Box maisonOui — SP RPI et SE sur la box maison✅ Fonctionne
2 — Wi-Fi tiersNon — SE sur le réseau du tiers, SP RPI chez Vincent❌ Probablement injoignable
3 — Hotspot Xiaomi + 4GNon — SE sur le subnet privé du hotspot, SP RPI chez Vincent❌ Probablement injoignable
4 — Hotspot Xiaomi sans 4GOui — SE et SP Smart sur le même hotspot✅ Fonctionne
En mode 2 et 3, SP (RPI) n'est tout simplement pas sur le réseau local où se trouve SE — aucune adresse locale ne peut le résoudre. C'est précisément le type de problème qu'un relai (nginx, tunnel, ou retour par MQTT plutôt que par HTTP direct) est censé résoudre. À ce jour, aucun mécanisme de ce type n'est implémenté — le commentaire RTMP/DuckDNS dans rz_camera_manager.sh (scénario "4K") est resté désactivé et ne couvre de toute façon que le cas d'une SIM dédiée, pas les modes 2/3 actuels.
Pistes à explorer en session dédiée : (a) SE pousse l'IP/URL courante vers SP via MQTT (qui fonctionne dans tous les modes car basé sur DuckDNS+NAT, pas sur une IP locale) puis SP affiche cette URL dans son navigateur local — mais ne résout pas le problème si SP n'a pas non plus d'accès réseau direct à SE ; (b) un tunnel inverse initié par SE (puisque c'est SE qui sait toujours joindre SP, jamais l'inverse) vers le RPI, exposant alors la caméra via le RPI lui-même ; (c) accepter que la caméra ne soit utilisable qu'en modes 1 et 4, et le documenter comme limitation connue plutôt que comme bug à corriger.
Bug résolu — accès distant cassé en IPv4, masqué par l'IPv6

Symptôme : accès au dashboard fonctionnel en Wi-Fi domicile, mais "connexion réinitialisée" depuis tout réseau externe (4G, Wi-Fi tiers).

Cause : robotz-vincent.duckdns.org résout l'IPv6 du RPi en priorité. Le Wi-Fi domicile a une connectivité IPv6 native (déléguée par la Livebox) — les tests y réussissaient toujours en IPv6, sans jamais valider l'IPv4. La règle NAT/PAT Livebox s'était désynchronisée en IPv4 (bug connu sur ce modèle de box) — silencieusement, sans signal visible dans l'interface. Le 4G (sans IPv6 fiable) révélait l'échec que le domicile masquait.

Correctif : supprimer puis recréer la règle NAT/PAT (renommée httpsRPI3, IP locale 192.168.1.40 saisie directement plutôt que via le nom d'équipement). Validé en conditions réelles (4G, Wi-Fi désactivé).

🪤 Piège de diagnostic à connaître : ne jamais tester l'IP publique de la box depuis un appareil connecté à cette même box — le NAT hairpin (loopback) n'est pas supporté par la Livebox et produit un faux négatif (timeout), même quand l'accès réel depuis l'extérieur fonctionne. Toujours valider depuis un réseau réellement externe.
⚠ Surveillance à prévoir : ce bug peut réapparaître (redémarrage box, mise à jour firmware). Mêmes symptômes si ça se reproduit : IPv6 OK, IPv4 cassé, échec visible seulement depuis un réseau sans IPv6 fiable. Même correctif : supprimer/recréer httpsRPI3.
💡 Connexion avec le problème caméra (modes 2/3) : nginx confirmé actif sur le RPi comme reverse proxy (voir section nginx ci-dessous) — exactement le type de mécanisme envisagé comme piste de résolution pour la portée caméra. Le même principe (un service exposé sur le RPi via nginx+NAT+DuckDNS, joignable depuis n'importe quel réseau) pourrait potentiellement servir de relai pour la caméra, via un tunnel initié par SE vers le RPi. À creuser en session dédiée caméra.
