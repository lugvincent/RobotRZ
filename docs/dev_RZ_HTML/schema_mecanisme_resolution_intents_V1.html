Mécanisme de résolution des intents à traitement particulier

Un seul mécanisme générique (ui_Traitement) pour TRADUCTION, CALCUL et MACRO — le routage ne regarde que la longueur du tableau d'intents retourné, jamais un type déclaré à l'avance.

Entrée / neutre
Décision / mécanisme générique
Cas > 1 intent (pré-validation groupée)
Chemin normal
Rejet / point ouvert
⚠️ Point bloquant pour la pré-validation groupée : SF_ReglesMinimales_V1 mélange aujourd'hui vérification et effet de bord — R7 fait un global.set dans sa branche de rejet, et R13 dépend d'un flag positionné juste avant par R5+R9 dans la même exécution. Utiliser ce sous-flow tel quel pour "essayer" un lot avant de savoir si on le garde modifierait déjà l'état pour rien en cas de rejet. À corriger avant de construire ce mécanisme, pas après.

Structure de la table ui_Traitement (inventaire des fonctions de résolution)

id_traitementref_fonctionparamlabel (info admin)
CONV_COULEUR_BASElookup_liste{liste:"LISTE_COULEURS_RGB"}traduction couleur
SCALE_LINEAIREscale_lineaire{min:0, max:255}calcul (ex : LRING_BRIGHTNESS)
EXPAND_MACROexpand_macro{} (lit id_fils du contexte)macro (ex : MACRO_PAUSE)
EXPR_EMOTIONexpr_emotion_multi{liste:"LISTE_EMOTIONS_RENDU"}macro paramétrée (ex : joie → 3 intents)

Un petit nombre de fonctions génériques, réutilisées via param — pas une ligne par commande. label est purement descriptif : il n'influence jamais le routage, qui ne dépend que du nombre d'intents réellement retourné par ref_fonction.

Terminologie Table D (colonne Traitement) : LocalSE (100% résolu sur SE, jamais de id_traitement) · SIMPLE (pas de id_traitement) · TRADUCTION · CALCUL · MACRO — ces trois derniers renseignent tous un id_traitement et suivent le même mécanisme ci-dessus.
