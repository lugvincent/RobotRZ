Tables de données

4 tables structurent les données du projet. Chacune a un rôle distinct et une source d'autorité. La Table A est normative mais jamais utilisée à l'exécution.

A
Table A — Référence normative VPIV
Travail : TableA_updatedV3.csv (253 lignes) — Référence figée : table_A_SE_v3.ods, LibreOffice Calc
Document de référence pour le développement. Définit toutes les variables VPIV du projet : leur CAT, VAR, PROP, les valeurs possibles, les instances, les directions, les sources émettrices.

Usage : Consultation lors du développement. Jamais chargée ni utilisée à l'exécution. C'est la source de vérité pour concevoir les trames et les scripts.

Champs principaux : SOURCE (P/S/A/E), VAR, PROP, INST, CAT, DIRECTION, NATURE, CYCLE, INTERFACE, FORMAT_VALUE, COMPLEXE, VPIV_EX, NOTES.
SOURCE E = soit SE soit Arduino peut émettre selon le contexte — pas les deux simultanément. Documente l'ambiguïté légitime de l'émetteur.
⚠️ Toujours croiser FORMAT_VALUE et COMPLEXE avant de juger qu'une propriété structurelle (objet imbriqué) est absente de la norme — COMPLEXE peut être O/N (flag simple, ex. Odom) ou contenir la structure détaillée d'un objet JSON imbriqué (ex. paraCam). Une vérification basée uniquement sur FORMAT_VALUE a fait croire à tort que paraCam n'existait pas (29 juin 2026).
B
Table B — enrichedVars (runtime Node-RED)
PC (dépôt Git) : node-red/config/globalSave.json
RPi réel (rzPath, settings.js) : /home/rzServeur/robotRZ/data/globalSave.json
Variables runtime de Node-RED. Chargées en mémoire au démarrage de SP depuis globalSave.json. Accessibles via global.get('enrichedVars').

Usage : Source d'initialisation que SP envoie vers SE et Arduino après réception de SE_READY. Éditables en temps réel via l'interface ui_VarG.

Volatile : Perdues si Node-RED redémarre sans sauvegarde. La Table C est la source persistante.
SP est l'autorité d'initialisation : après SE_READY, SP envoie les trames VPIV depuis enrichedVars vers SE et Arduino. Garantit la cohérence quelle que soit l'instance Node-RED active.
⚠️ Les deux chemins ci-dessus désignent deux fichiers distincts, pas le même fichier vu sous deux angles. Le chemin PC reflète l'arborescence du dépôt Git ; le chemin réel sur le RPi (déclaré dans settings.js → functionGlobalContext, variable rzPath) est celui effectivement lu/écrit à l'exécution.
C
Table C — courant_init.json
termux/config/courant_init.json — sur SE
Source unique persistante de la configuration SE et Arduino. Définit les modes de démarrage de chaque manager (OFF/FLOW/MOY/ALERTE…), les seuils, les fréquences, les paramètres matériels.

Usage : Lue par rz_start.sh pour décider quels managers démarrer. Lue par check_config.sh pour générer les fichiers *_runtime.json. Modifiable via ui_VarG côté SP.

Fichiers générés : gyro_runtime.json, mag_runtime.json, sys_runtime.json, cam_config.json, mic_config.json, stt_config.json, appli_config.json.
Les fichiers *_runtime.json sont générés par check_config.sh — non versionnés dans Git. À relancer si courant_init.json est modifié.
D
Table D — Catalogue commandes STT
termux/scripts/sensors/stt/table_d_catalogue.csv
Catalogue de toutes les commandes vocales reconnues par PocketSphinx. Associe chaque phrase au modeRZ requis, à la trame VPIV à émettre, et aux conditions de validité.

Usage : Consulté par rz_stt_handler.sh pour convertir une commande reconnue en trame VPIV. Si la commande n'est pas dans le catalogue, repli vers Gemini API.

Contexte dynamique : rz_state-manager.sh recalcule le sous-ensemble de commandes valides à chaque changement de modeRZ.
Module STT à développer. La Table D existe en structure mais le manager rz_stt_manager.sh n'est pas encore opérationnel.

Vade-mecum — Gestion des tables
Procédures complètes pour ajouter, supprimer ou modifier une variable. Chaîne de dépendances A→B→C, matrice des fichiers impactés, exemples concrets (ajout Appli.IA_conv, suppression Appli.Baby), pièges et checklist de clôture.
vademecum_tables_V1.html
keys.json — fichier sensible hors tables
Fichier de credentials — jamais dans Git. À créer manuellement après chaque git clone.

Chemin : termux/config/keys.json

Contenu (format étendu depuis 01/07/2026) : GEMINI_API_KEY, MQTT_USER, MQTT_PASS, MQTT_HOST, DUCKDNS_TOKEN, GITHUB_USER, GITHUB_TOKEN

Mise à jour du remote Git : toujours via termux/config/config_Et_actualisation_code/set_git_remote.sh — jamais à la main.
