Sécurité

Règles de sécurité du projet RobotRZ. Plusieurs incidents ont forgé ces règles — elles ne sont pas théoriques.

Incidents de sécurité — leçons apprises
Incident 1 — Injection de flux Node-RED (28 avril 2026)
Un flux Node-RED malveillant a été injecté via l'interface Node-RED exposée sans authentification sur internet via DuckDNS. Le flux tentait de créer un utilisateur système (jim) avec des droits sudo.

Résultat : La commande a échoué, aucun utilisateur créé, aucun accès SSH suspect confirmé dans les logs. Le flux a été supprimé immédiatement.

Actions correctives :
— adminAuth activé dans settings.js (login/mot de passe obligatoire)
— Vérification complète des logs SSH
— Audit de tous les flows existants
Incident 2 — Clé API Gemini exposée dans Git
La clé API Gemini a été committée dans le dépôt Git puis découverte dans l'historique.

Actions correctives :
— Clé révoquée immédiatement sur Google Cloud Console
— Nouvelle clé générée
— Historique Git purgé via git filter-branch
— keys.json ajouté au .gitignore
— Vérification qu'aucune autre clé n'était exposée
Incident 3 — Credentials exposés en clair pendant tests SSH (29 juin 2026)
Le mot de passe MQTT (MQTT_PASS) et la clé API Gemini (déjà régénérée une première fois après l'incident 2) sont réapparus en clair plusieurs fois dans les échanges de la session — copier-coller de commandes et de fichiers de config pendant le diagnostic SSH du pattern LockSE.

Actions correctives — faites le 01/07/2026 :
— MQTT_PASS régénéré côté Mosquitto (RPi), keys.json (Doro) et broker Node-RED (SP RPI) — 3 emplacements, testé par mosquitto_pub
— Clé API Gemini régénérée sur Google AI Studio (nouveau format, 53 caractères)

Bonne pratique adoptée pour la suite : charger les credentials dans une variable shell sans jamais les afficher, et vérifier qu'elle est bien chargée par sa longueur plutôt que sa valeur — utile aussi pour diagnostiquer une session SSH expirée (variable perdue).
MQTT_PASS=$(jq -r '.MQTT_PASS' keys.json) echo "${#MQTT_PASS}" # affiche la longueur, jamais la valeur
✅ Résolu — 01/07/2026
Incident 4 — Token GitHub supprimé par erreur (1er juillet 2026)
Vincent a supprimé un token GitHub pensant qu'il était inutilisé. Conséquence : la synchronisation GitHub → Project Knowledge Claude a cessé de fonctionner. Le diagnostic a révélé que le remote Git sur le Doro (Termux) contenait le token en clair dans l'URL (https://USER:TOKEN@github.com/...) — exposé accidentellement dans une conversation pendant le diagnostic, donc traité comme compromis et révoqué immédiatement, quel que soit son état initial.

Actions correctives :
— Nouveau token GitHub fine-grained créé : portée limitée au dépôt RobotRZ uniquement (pas "All repositories"), permission Contents → Read and write seule, expiration 90 jours
— Script set_git_remote.sh créé pour ne plus jamais manipuler l'URL du remote à la main
— Constat : PC (VS Code) et Doro (Termux) utilisent deux mécanismes d'authentification différents — Windows Git Credential Manager (opaque, token non visible) vs URL avec token embarqué (Termux, visible via git remote -v). Supprimer un token ne casse que les clients qui l'utilisent directement.

✅ Résolu — 01/07/2026

config_Et_actualisation_code/ — outillage de rotation des credentials
Nouveau dossier termux/config/config_Et_actualisation_code/ — point d'entrée unique pour toute procédure d'actualisation de credential, créé pour répondre à la désorganisation chronique liée au grand nombre de composants du projet.
termux/config/config_Et_actualisation_code/ ├── set_git_remote.sh # Met à jour le remote Git depuis keys.json └── README_config_Et_actualisation_code.md # v1.1 — guide de renouvellement (GitHub, Gemini, MQTT, DuckDNS, git clone)
set_git_remote.sh lit GITHUB_USER et GITHUB_TOKEN depuis keys.json, met à jour le remote, fait un git fetch de validation. Vérifie les credentials par longueur uniquement. À relancer après chaque renouvellement de token ou git clone.
GitHub — token fine-grained : piège à connaître
⚠ L'option "Public repositories" (sélectionnée par défaut à la création) donne un accès lecture seule aux dépôts publics, sans aucune permission d'écriture — aucun push possible. Choisir impérativement "Only select repositories" → sélectionner RobotRZ → permission Contents → Read and write.
