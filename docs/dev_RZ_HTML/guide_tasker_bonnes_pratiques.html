02

XML importé vs création via interface graphique

Pourquoi le XML importé génère des bugs

  • Codes actions variables : changent entre versions Tasker (voir section 1)
  • Structure des arguments : format et nombre d'args différents selon version (Int vs Str, ve="3" vs ve="2"...)
  • Attributs manquants : un arg manquant dans le XML = comportement imprévisible sans message d'erreur
  • IDs conflictuels : si l'ID existe déjà → Tasker peut refuser ou créer un doublon
  • Scènes avec embedded tasks : les tâches internes à une scène ont un format spécifique difficile à reproduire manuellement
  • Encodage XML : &gt;, &lt;, &amp; doivent être correctement échappés

✅ Quand utiliser le XML

  • Reproduire une tâche déjà exportée depuis CE Doro
  • Tâches simples (≤3 actions) avec codes validés
  • Déploiement rapide de tâches identiques
  • Backup et restauration du projet

⚠️ Préférer l'interface graphique pour

  • Toute tâche complexe (JavaScriplet, conditions)
  • Actions avec plugins (Termux:Tasker, IP Webcam...)
  • Scènes avec boutons et tâches internes
  • Première création d'une action inconnue
  • Tout ce qui n'a pas été testé sur CE device

💡 Workflow recommandé

  • 1. Créer via l'UI Tasker → tester → valider
  • 2. Exporter depuis Tasker (appui long → Exporter)
  • 3. Le fichier exporté = référence pour reproduire
  • 4. Pour du XML généré : toujours baser sur un export existant du même device comme template

JavaScriptlet — règles et limitations

🚫 Interdit dans un JavaScriptlet Tasker

  • return au niveau global — return n'est valide qu'À L'INTÉRIEUR d'une fonction. Hors fonction = crash "Illegal return statement"
  • Arrays globaux — setGlobal('arr', [1,2,3]) ne fonctionne pas (limitation Android)
  • %variables directement — les variables globales Tasker (%MAJ) ne sont PAS accessibles directement, utiliser global('NOM')
  • Exécution parallèle — un seul JavaScriptlet à la fois. Si un autre tourne, le second attend.

✅ Règles correctes

OpérationSyntaxe correcteErreur courante
Lire variable globaleglobal('RZparam')%RZparam (ne marche pas)
Écrire variable globalesetGlobal('RZparam', 'On')setGlobal('%RZparam', ...)

Tableau localvar arr = [1,2,3]; → fonctionneTableau global → ne fonctionne pas

Pattern correct — remplacer return par if/else

// ❌ FAUX — return hors fonction
var cmd = applis[btn];
if (!cmd) { setGlobal('result', ''); return; }
setGlobal('result', cmd.val);

// ✅ CORRECT — if/else
var cmd = applis[btn];
if (cmd) {
    setGlobal('result', cmd.val);
} else {
    setGlobal('result', '');
}

Pattern correct — return DANS une fonction (autorisé)

function getMode(btn) {
    var modes = {veille:'1', fixe:'2', deplacement:'3', arret:'0'};
    return modes[btn] || '1';  // ✅ return dans une fonction = OK
}
var val = getMode(global('RZmenuBtn'));
setGlobal('RZmodeVal', val);

Règles scènes — enchaînements obligatoires

🚫 Erreur : scene already visible

Afficher (code 47) une scène déjà visible → crash
Fix : toujours code 49 (Destroy) avant code 47 (Show)

🚫 Erreur : éléments non initialisés

Modifier un élément scène immédiatement après Show → rien ne se passe
Fix : attendre 500ms (code 30) après code 47

Séquence correcte — Show + écriture élément

code 49  → Destroy RZ_Expression   (silencieux si absente)
code 47  → Show RZ_Expression
code 30  → Wait 500ms
code 51  → Set emoji_expression = 😐

Boutons de scène — règle Destroy avant action

// Chaque bouton de RZ_Menu doit :
code 547 → Set %RZparam = On     (si paramètre nécessaire)
code 49  → Destroy RZ_Menu       (AVANT l'action métier)
code 130 → Perform Task RZ_Baby  (action métier)
06

Génération XML fiable — règles de base

Règles de génération XML validées

  • Baser sur un export du Doro : le seul XML fiable est celui exporté par Tasker lui-même depuis ce device
  • &gt; obligatoire : le caractère > dans les chaînes XML doit être &gt;
  • &lt; obligatoire : le caractère < dans les chaînes XML doit être &lt;
  • code 547 : toujours arg5=3 (scope global) et arg6=1 — sinon variable locale seulement
  • Chaîne vide : utiliser <Str sr="argN" ve="3"/> (self-closing) et NON <Str ...></Str>
  • Chemin fichier code 410 : chemin RELATIF depuis /storage/emulated/0/ — ex: Tasker/RobotRZ/vpiv_out.txt
  • Pas de commentaires XML : les <!-- ... --> dans les fichiers à importer peuvent poser problème
  • Pas d'indentation : le XML importable doit être compact (une ligne ou sans indentation inutile)
  • IDs : Tasker réassigne les IDs à l'import — ne pas se fier aux IDs pour les liens entre éléments, utiliser les noms (<nme>)

Workflow recommandé pour générer du XML fiable

  • 1. Créer la tâche de référence via l'UI Tasker sur le Doro
  • 2. L'exporter (appui long → Exporter → Vers un fichier)
  • 3. Utiliser ce XML exporté comme template
  • 4. Modifier uniquement le contenu (labels, valeurs, noms de tâches)
  • 5. Ne jamais modifier les codes d'action sans avoir une référence exportée du Doro
07

Checklist avant d'importer un XML

  • ☐ Tous les codes d'action sont-ils validés sur ce Doro ?
  • ☐ Les chaînes avec > ou < sont-elles échappées en &gt; / &lt; ?
  • ☐ Les JavaScriptlets ne contiennent-ils pas de return au niveau global ?
  • ☐ Les variables globales sont-elles lues via global() et écrites via setGlobal() ?
  • ☐ L'ancienne version de la tâche a-t-elle été supprimée dans Tasker avant import ?
  • ☐ Pour les scènes : le code 49 (Destroy) précède-t-il chaque code 47 (Show) ?
  • ☐ code 547 : arg5=3 et arg6=1 sont-ils présents pour les variables globales ?
  • ☐ Les chemins de fichiers (code 410/417) sont-ils relatifs depuis /storage/emulated/0/ ?
