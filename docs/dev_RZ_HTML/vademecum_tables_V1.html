Section 1
Architecture des quatre tables

Chaque table a un rôle distinct et une autorité précise. Elles ne sont pas interchangeables.

A Table A — Référence normative VPIV
Fichier : table_A_SE_v3.ods (LibreOffice Calc)

Source de vérité du développement. Définit toutes les variables VPIV : CAT, VAR, PROP, TYPE, DIRECTION, CYCLE, NATURE, FORMAT, instances, codage, exemple VPIV, notes.

Jamais chargée à l'exécution. Consultée pour concevoir, jamais pour faire tourner le code.
C Table C — courant_init (.sh → .json)
Source : courant_init.sh (v5.1)
Sortie : courant_init.json

Configuration opérationnelle persistante de SE et Arduino. Seul fichier à éditer manuellement en développement. Contient les valeurs initiales de tous les modules. Synchronisée sur SP au démarrage.
B Table B — enrichedVars (runtime Node-RED)
Fichier disque : globalSave.json (sur SP)
En RAM : global.get('enrichedVars')

Variables runtime Node-RED. Chargées au démarrage de SP depuis globalSave.json. Éditables via ui_VarG. Ne pas confondre avec global.json de SE (variables transverses SE, structure différente).
D Table D — Catalogue STT
Fichier : tableD_catalogueV2.csv

Catalogue des commandes vocales. Fait le pont entre ID vocaux et trames VPIV (VAR/PROP des autres tables). Générée par original_init.sh. Fera l'objet d'un vade-mecum séparé.

Section 4
Cas A — Ajouter une variable
1
Table A — Ajouter la ligne dans l'ODS A
Ouvrir table_A_SE_v3.ods dans LibreOffice Calc. Ajouter une ligne dans la section VAR concernée (respecter l'ordre alphabétique des VAR). Renseigner tous les champs : SOURCE, VAR, PROP, CAT, TYPE, FORMAT_VALUE, CODAGE, DIRECTION, INSTANCE, COMPLEXE, CYCLE, NATURE, INTERFACE, VPIV_EX, NOTES.
Si la variable a plusieurs CAT (V + I = commande + ACK), ajouter autant de lignes que nécessaire.
2
courant_init.sh — Ajouter la variable C
Dans le bloc de la section concernée, déclarer la variable Bash et l'ajouter dans le heredoc JSON de génération. Respecter la structure existante des autres variables du même bloc.
Ajouter aussi un commentaire explicatif comme pour les autres variables.
3
original_init.sh — Même ajout C
Reproduire exactement les mêmes ajouts dans original_init.sh. Les deux fichiers doivent rester structurellement identiques — seules les valeurs peuvent différer (dev vs production).
Si la variable est pilotable vocalement, ajouter aussi la ligne correspondante dans la section catalogue STT de original_init.sh.
4
check_config.sh — Ajouter la lecture et validation si nécessaire SE
Si la variable doit être extraite et validée par check_config.sh (ex : champ d'un bloc existant comme appli), ajouter la ligne lire_json correspondante et la ligne de génération dans le heredoc JSON du fichier de sortie.
5
Régénérer courant_init.json SE
bash courant_init.sh
Vérifier que le JSON généré est valide : python3 -m json.tool courant_init.json
6
Régénérer les *_config.json SE
bash check_config.sh
Vérifier le log de sortie — aucune ligne ERREUR ne doit apparaître.
7
rz_appli_manager.sh — Ajouter le routage si CAT=A SE
Si la nouvelle variable est de CAT=A (commande applicative Android), ajouter un case dans la fonction route_appli() avec la tâche Tasker correspondante. Mettre à jour l'entête du script (TABLE DE ROUTAGE et VPIV ENTRANTS).
8
Table B — Mettre à jour globalSave.json via ui_VarG SP
Dans Node-RED, utiliser l'interface ui_VarG pour ajouter la nouvelle variable dans enrichedVars. Puis déclencher le flow admin de rechargement (reload globalSave) pour que la variable soit disponible en RAM via global.get('enrichedVars').
9
Commit Git + déploiement SE SE SP
Commiter les fichiers modifiés. Déployer sur le smartphone SE via Git. Vérifier que la variable apparaît bien dans courant_init.json déployé.
Section 5
Cas B — Supprimer une variable
⚠️ Précaution avant suppression : Vérifier dans tous les scripts SE (rz_*_manager.sh, rz_vpiv_parser.sh, rz_state-manager.sh, rz_stt_handler.sh) et dans les flows Node-RED qu'aucune référence à cette variable n'est active. Une suppression partielle laisse des références mortes qui causent des erreurs silencieuses.
1
Audit des références avant toute modification
Rechercher le nom de la variable (PROP) dans tous les scripts SE et flows Node-RED.
grep -rn "NomVariable" ~/robotRZ-smartSE/termux/scripts/
Lister toutes les occurrences à supprimer ou adapter.
2
Table A — Supprimer ou marquer la ligne A
Option 1 : supprimer la ligne directement.
Option 2 (recommandée pendant la transition) : mettre la ligne en commentaire dans une couleur distincte et noter la date de suppression. Supprimer définitivement à la prochaine version de la table.
3
courant_init.sh — Supprimer la variable et sa ligne JSON C
Supprimer la déclaration Bash de la variable et la ligne correspondante dans le heredoc JSON. Vérifier que la virgule finale de la ligne précédente est correcte (JSON strict : pas de virgule trailing).
4
original_init.sh — Même suppression C
Reproduire exactement la même suppression. Si la variable avait une commande vocale dans la section catalogue STT, supprimer aussi la ligne CSV correspondante.
5
check_config.sh — Supprimer la lecture et la génération SE
Supprimer la ligne lire_json, la validation éventuelle, et la ligne dans le heredoc JSON de génération. Vérifier les boucles de validation : si la variable était incluse dans une boucle for app_state in ..., la retirer.
6
rz_appli_manager.sh — Supprimer le case si CAT=A SE
Retirer le bloc case correspondant dans route_appli(). Mettre à jour l'entête (TABLE DE ROUTAGE et VPIV ENTRANTS).
7
Régénérer courant_init.json et les *_config.json SE
bash courant_init.sh && bash check_config.sh
Vérifier l'absence d'erreurs. Contrôler que la variable n'apparaît plus dans appli_config.json.
8
Table B — Supprimer la variable de globalSave.json SP
Via ui_VarG dans Node-RED : supprimer l'entrée enrichedVars correspondante. Déclencher le flow admin de rechargement.
9
Flows Node-RED — Vérifier les références SP
Rechercher la PROP supprimée dans tous les nœuds Function de Node-RED. Toute référence morte à global.get('NomVariable') doit être retirée ou remplacée.
Section 6
Cas C — Modifier une valeur (sans changer la structure)

C'est le cas le plus simple. La variable existe déjà partout, on change uniquement sa valeur initiale ou ses seuils.

1
courant_init.sh — Changer la valeur C
Trouver la variable Bash et modifier sa valeur. Respecter les unités documentées en Table A (ex : degrés×10, Hz vs secondes selon le module).
2
original_init.sh — Adapter si besoin C
Si la valeur de production doit aussi changer, modifier original_init.sh en cohérence.
3
Table A — Mettre à jour la colonne FORMAT_VALUE ou NOTES A
Si la valeur par défaut ou la plage change, mettre à jour la Table A pour rester normative.
4
Régénérer + synchroniser SE SP
bash courant_init.sh && bash check_config.sh
Puis mettre à jour globalSave.json via ui_VarG si la valeur initiale enrichedVars doit aussi changer.

Contexte : IA_conv est un nouveau PROP dans VAR=Appli. Elle permet à SP d'activer/désactiver la conversation IA sur SE (Gemini). Structure identique aux autres apps Appli : commande On|Off depuis SP (CAT=A), ACK OK|FAIL depuis SE (CAT=I).

Section 9
Synchronisation SP ↔ SE après modification
Flux de synchronisation au démarrage robot
Après toute modification de variable, voici l'ordre à respecter au prochain démarrage pour que SP et SE soient cohérents :
①
SE démarre — charge courant_init.json SE
rz_start.sh lit courant_init.json → démarre les managers avec les valeurs initiales. SE envoie $I:COM:info:SE:SE_READY# sur MQTT.
②
SP reçoit SE_READY — envoie la configuration via VPIV SP
SP (maître absolu) envoie depuis enrichedVars les trames VPIV de configuration vers SE. C'est la valeur SP qui écrase la valeur initiale de SE. SP est la source de vérité à l'exécution.
③
SE met à jour ses fichiers runtime SE
Chaque manager reçoit les nouvelles valeurs via VPIV et met à jour son fichier *_runtime.json / *_config.json local.
⚠️ Conséquence pratique : si une variable est ajoutée dans courant_init.json de SE mais pas encore dans enrichedVars de SP, SE démarre avec la valeur locale mais SP ne l'enverra pas → incohérence. Il faut toujours mettre à jour globalSave.json (Table B) en même temps que courant_init.sh (Table C).
Procédure de rechargement globalSave.json sur SP
Après modification de globalSave.json via ui_VarG :
// Dans le flow admin Node-RED (nœud Function + Inject) // Déclencher : "reload globalSave" const nodeFs = global.get("nodeFs"); const filePath = global.get("rzPath"); const raw = nodeFs.readFileSync(filePath, 'utf8'); const parsed = JSON.parse(raw); global.set("enrichedVars", parsed.enrichedVars); // → enrichedVars en RAM est maintenant synchronisé avec le fichier disque
Section 10
Pièges connus et règles absolues
⚠️ Jamais éditer courant_init.json à la main
Ce fichier est généré. Toute modification manuelle sera écrasée au prochain bash courant_init.sh. Source unique = courant_init.sh.
⚠️ Virgules JSON dans les heredoc
Lors d'un ajout ou d'une suppression dans un bloc JSON, vérifier que la dernière ligne du bloc n'a pas de virgule trainante — JSON strict ne le tolère pas. Valider avec python3 -m json.tool.
⚠️ courant_init.sh ≠ original_init.sh — maintenir en parallèle
Les deux fichiers ont la même structure mais des valeurs potentiellement différentes. Toute modification structurelle (ajout/suppression de variable) doit être répercutée dans les deux. Un script modifié sans l'autre → incohérence production/dev.
⚠️ Unités fréquences — trois régimes différents
Gyro/Mag : freqCont en Hz. Sys : freqCont en secondes. MicroSE : freqCont en ms. Ne pas mélanger — sens inverse selon le module. Voir Table A colonne CODAGE.
⚠️ TorchSE — bug VAR connu
rz_torch_manager.sh émet $I:Torch:... au lieu de $I:TorchSE:.... Signalé en Table A feuille Légende. À corriger avant d'ajouter des variables TorchSE.
⚠️ enrichedVars ≠ courant_init.json en RAM
enrichedVars (Table B) est la copie en RAM de globalSave.json côté SP. Ce n'est pas une copie de courant_init.json. Ne jamais copier courant_init.json dans globalSave.json directement — structures différentes.
ℹ️ global.json SE ≠ globalSave.json SP
global.json côté SE contient les variables transverses runtime (CfgS, Urg, Sys, STT…). globalSave.json côté SP contient enrichedVars. Deux fichiers distincts, structures différentes, ne pas confondre.
ℹ️ Variables Tasker non stockées sur SP
Les variables internes Tasker (pin Doro, numéros de task, etc.) ne transitent pas par VPIV et ne figurent pas dans les tables. Les packages Android et noms de tâches sont dans courant_init.sh et dans appli_config.json.
