Feuille de route — Développement Node-RED (SP)

Document préparatoire pour reprendre le développement de SP. Synthétise l'état réel du code existant, ce que les autres sous-systèmes attendent désormais de SP, et propose une séquence de travail structurée.

🎯
Pourquoi Node-RED devient le chantier prioritaire
Arduino, SE et Tasker sont aujourd'hui les sous-systèmes les plus avancés du projet. Les modules capteurs/actionneurs/applications sont définis, les Tables A à D sont stabilisées, le pipeline vocal Option B est validé. SP (Node-RED) est désormais le goulot d'étranglement : c'est le seul maillon qui n'a pas suivi le même rythme de maturation, alors qu'il est le maître absolu du système.
Rôle de SP — rappel synthétique

SP est le maître absolu du système. Il décide, SE et Arduino exécutent. SP désigne une fonction (pilotage Node-RED) assurée par SP RPI (référence) ou SP Smart (Xiaomi, secours local). Tout le détail architectural — broker MQTT, onglets, contexte global, convention de nommage des flows — est dans sp_nodeRED_V1.html. Ce document-ci se concentre sur la suite des opérations, pas sur la description de l'existant.

Ce qui a changé depuis mars — à absorber maintenant

Le code Node-RED date de mars. Depuis, plusieurs décisions structurantes ont été prises côté SE/Tasker que Gtion_Init et Gtion_EtatGlobal doivent désormais intégrer :

Architecture STT Option B (21 juin)
SE calcule désormais STT.context (Inactif/Cmde/Conv/Mixte) à partir de modeRZ ET de Mtr.state. SP doit relayer Mtr.state reçu d'Arduino vers SE — sans ce câblage, la sécurité "VEILLE + mouvement" ne fonctionne pas. C'est un input direct pour Gtion_Init ou un sous-flow dédié.
Garde-fous STTcontext (identifiés 21 juin, jamais implémentés)
Bloquer Mixte si typePtge=3 (laisse) ET modeRZ=3 (déplacement). Avertir si VEILLE+Mixte. Ce sont des règles métier — leur place naturelle est Gtion_EtatGlobal / SF_ReglesMinimales, pas SE.
Appli.IA_Conv (créé côté SE/Tasker mi-juin, jamais intégré côté SP)
RZ_IA_Conv existe et fonctionne dans Tasker. Côté SP : aucune ligne Table A (CAT=A/I), aucune entrée enrichedVars via ui_VarG. SP ne peut donc pas encore piloter ce module depuis l'extérieur (UI, autre logique).
Table D stabilisée à 71 commandes
Référence catalogue désormais fiable (séparateur pipe confirmé, CAM/Lring/SYS corrigés). Utile pour valider que chaque commande catalogue a bien son pendant dans Gtion_EtatGlobal / les futurs M_Act_.
Feuille de route proposée — 6 phases

Cette séquence combine l'ordre de priorité que tu avais toi-même fixé en mars (CfgS → Urg → COM → Sys → Gyro/Mag → CamSE → MicroSE → Appli → STT) avec la convention de nommage validée en mai (Bus_/Gtion_/M_Capt_/M_Act_/ui_) et les besoins fonctionnels apparus en juin. Chaque phase est testable indépendamment avant de passer à la suivante.

0
Reconnecter le Bus à la réalité
Bus_GestionFlux (ex RZ_GestionFlux_V1) — prérequis absolu

Le bus est structurellement sain mais parle un langage interne théorique. Avant toute chose, il doit parler le vrai protocole.

  • Remplacer le contrat de message interne (source/eventType/intent/payload) par un vrai parsing VPIV ($CAT:VAR:PROP:INST:VAL#)
  • Brancher sur les vrais topics MQTT : SE/statut (in), SE/commande (out), SE/arduino/data (in), SE/arduino (out)
  • Alimenter le contexte global réel global.RZ_<VAR> à chaque trame reçue (déjà conçu, à implémenter concrètement)
  • Renommer la tab en Bus_GestionFlux (convention mai)
Sans cette phase, rien de ce qui suit ne peut être testé avec de vraies données.
1
Rendre Gtion_Init réellement fonctionnel
SF_Init_1 à 4 — sortir du STUB

C'est le flow le moins mûr alors qu'il est sur le chemin critique. La séquence exacte à implémenter existe déjà — rédigée par toi en mars (section 15 de doc_prep_SE_nodeRED.docx).

  • SF_Init_1 : charger un vrai fichier enrichedVars (Table B), pas un stub
  • SF_Init_2 : détection réseau réelle (au minimum lire la config, le scan actif peut attendre)
  • SF_Init_3 : attendre le vrai SE_READY (déjà émis par rz_start.sh — confirmé dans le code SE) + boot Arduino
  • SF_Init_4 : envoyer la séquence VPIV réelle vers SE — 9 étapes déjà spécifiées : typeReseau → typePtge → modeRZ=VEILLE → Sys.modeSys → Gyro/Mag → MicroSE/CamSE → STT.modeSTT → modeRZ final
  • Prévoir le délai/retry au boot (SE peut ne pas encore écouter MQTT quand SP envoie — paradoxe d'amorçage documenté)
Dépend de la Phase 0 (Bus réel) pour pouvoir effectivement envoyer/recevoir les trames.
2
Valider Gtion_EtatGlobal avec de vraies données
CfgS (modeRZ, typePtge) puis Urg — priorité métier n°1

Le cœur décisionnel existe et est audité positivement. Il n'a simplement jamais tourné en conditions réelles. C'est ici qu'on le branche et qu'on le teste pour de vrai.

  • Tester les transitions modeRZ avec un SE réel connecté (ARRET↔VEILLE↔FIXE↔DEPLACEMENT↔AUTONOME)
  • Vérifier les invariants en conditions réelles (retour VEILLE toujours possible, ARRET prioritaire…)
  • Brancher Urg : réception source(E)/etat(I), commande clear(V) — priorité 0 du flow, déjà structurée
  • Brancher COM : debug/info/warn/error pour affichage console SP
Dépend des Phases 0 et 1. C'est le premier moment où le système devient réellement piloté de bout en bout.
3
Câblage Mtr.state et garde-fous STTcontext
Les 2 chantiers identifiés le 21 juin — leur place naturelle

Ces deux chantiers ont été identifiés en aval (côté STT) mais leur implémentation est entièrement côté SP. Ils prennent place ici car ils dépendent de CfgS/Urg fonctionnels.

  • Relayer la trame Mtr.state reçue d'Arduino vers SE : $I:Mtr:state:*:L,R,A# sur SE/commande
  • Règle Gtion_EtatGlobal : bloquer STTcontext=Mixte si typePtge=3 (laisse) ET modeRZ=3 (déplacement)
  • Règle Gtion_EtatGlobal : avertissement (pas blocage) si modeRZ=1 (VEILLE) avec Mixte actif
Dépend de la Phase 2. Sans Mtr réellement câblé (Arduino→SP), Mtr.state n'a pas de valeur réelle à relayer.
4
Modules de supervision et commande — M_Capt_ / M_Act_
Ordre suggéré : Sys (✓) → Gyro/Mag (✓) → Mtr/US/SecMvt → Srv/Lring/Lrub → CamSE → MicroSE → Appli → STT

Sys, Gyro et Mag sont déjà couverts par Gtion_Statut SE (opérationnel). Le travail restant porte sur les modules Arduino et les modules SE encore non instrumentés côté SP.

Arduino restants (10 VAR)
Mtr · US · SecMvt · Odom · Srv · Lring · Lrub · Mic · FS · IRmvt
SE restants (4 VAR)
CamSE · MicroSE · Appli (dont IA_Conv) · STT
  • Pour chaque VAR : un flow M_Capt_ (lecture/supervision) ou M_Act_ (commande) selon la nature
  • Mtr et US en premier — nécessaires pour exploiter pleinement les garde-fous de la Phase 3
  • Appli.IA_Conv : ajouter la ligne Table A manquante (CAT=A et CAT=I) + entrée ui_VarG — déverrouille le pilotage SP de la conversation Gemini
Peut démarrer dès la Phase 2 validée — les modules sont indépendants entre eux, priorisables librement selon l'envie du moment.
5
Interfaces utilisateur — ui_
ui_Accueil, ui_Pilotage, ui_STT, ui_Joystick

Volontairement en dernier — l'UI ne doit jamais être source de vérité (invariant déjà validé), donc elle n'a de sens qu'une fois la logique métier réellement opérationnelle derrière.

  • Finaliser ui_Accueil — liens vers Gtion_EtatGlobal via UI_Map_StateLevel
  • ui_Pilotage — interface pilotage temps réel (retour caméra, état Mtr/Odom)
  • ui_STT — visualisation contexte vocal, debug routage Cmde/Conv/Mixte

Décisions à prendre avant de commencer
1. Repartir du code de mars ou recommencer le Bus à neuf ?
Le format de message interne théorique (source/eventType/intent/payload) de RZ_GestionFlux_V1 a-t-il un intérêt à être conservé, ou vaut-il mieux l'abandonner directement pour un parsing VPIV réel plus simple ? La structure générale (1 seul point de sortie EVT_RAW_IN) reste valable dans les deux cas.
2. Granularité des flows M_Capt_/M_Act_
Un flow Node-RED par VAR (13 pour Arduino) ou des flows groupés par catégorie (ex. un seul flow "Capteurs Arduino" couvrant Mic/US/FS/IRmvt) ? Impacte directement le volume de travail de la Phase 4.
3. SF_ReglesDynamiques — la rebrancher maintenant ou rester V1 ?
Volontairement débranchée jusqu'ici. Les garde-fous STTcontext (Phase 3) pourraient être une première occasion concrète de la réactiver, ou rester des règles minimales codées en dur pour l'instant.
